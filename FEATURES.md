# NFL Win Probability Model — Feature Reference

This document describes every variable in the `games_with_features` table, produced by running:

```bash
python src/fetch_data.py
python src/build_features.py
```

Source data comes from [`nflreadpy`](https://github.com/nflverse/nflreadpy), covering the 2015–2025 seasons (3028 games, 60+ model features as of this revision). Live predictions for upcoming games are generated by `src/predict_engine/matchup.py` and `src/predict_engine/snapshots.py`, served via a FastAPI + Jinja2 web app deployed on Render at [nflwinprobability.com](https://nflwinprobability.com).

*(This app was originally built and deployed on Streamlit Community Cloud. It has since moved to a custom FastAPI backend for more control over the UI and served pages, with the domain purchased separately and pointed at Render via DNS.)*

## Plain-Language Glossary

- **EPA (Expected Points Added)**: how much a play helped or hurt a team's scoring chances vs. expectation.
- **Elo rating**: a "power ranking" number, borrowed from chess. Starts every team at 0 (league average); beating a strong team raises it more than beating a weak one.
- **Rolling average**: how a team/player has done *lately* (e.g. last 5 games), not full-season or career numbers.
- **Correlation**: a number from -1 to +1 measuring how strongly two things move together. The biggest single correlation in this whole project is about 0.19 — NFL outcomes are genuinely hard to predict.
- **Leakage-free**: a feature only ever uses games *before* the one being predicted.
- **Depth chart**: a team's own official ranked list of who plays each position — more reliable than "whoever played most recently."
- **Calibration**: whether a model's stated probability matches reality (e.g. do "70% chance" predictions actually come true ~70% of the time?).
- **CPOE / NextGen Stats**: NFL player-tracking data (from chips players wear) measuring physical movement — separation, time to throw, etc. — rather than box-score outcomes.
- **Held-out test**: measuring a feature's real value by training with vs. without it on a train/test split the model never saw during training, rather than trusting a raw correlation number.

### A full round of "how do we improve accuracy further"

A systematic investigation was run covering algorithm choice, feature selection, calibration, and several new feature ideas. Documented here in full so none of this needs to be re-attempted blindly:

**Didn't help:**
- **L1-regularized logistic regression**: cross-validation chose almost no penalty (`C≈167`), zero features shrunk to zero. Accuracy identical to plain logistic regression (67.9% vs 67.7%). *The existing feature set isn't carrying obvious dead weight.*
- **Random Forest / XGBoost**, re-tested on the full mature feature set: all algorithms within ~1pt of each other under `TimeSeriesSplit` CV (62.0–62.9%). *Algorithm choice is not the lever — stick with logistic regression.*
- **Isotonic calibration**: didn't fix a real, well-supported gap in the 40–50% predicted-probability range (model says ~45%, actual home win rate ~32%, n=100+). **Documented as an unresolved, known limitation** — may simply reflect that near-coin-flip games are inherently the hardest to call, or may be revisitable with more seasons of data.
- **Red zone TD rate** (built from play-by-play, per-drive): real signal (57.9% vs 53.0% home win rate) but redundant with Elo/point differential, -0.2pts.
- **Two-minute-drill comeback rate**: real signal after fixing a leakage bug (56.9% vs 52.9%), redundant, -0.7pts.
- **Explicit matchup interaction terms** (`home_off_rating - away_def_rating`, computed by hand): -1.4pts. Logistic regression can already approximate this combination from the separate offense/defense inputs; handing it the pre-computed version just adds a redundant, correlated column.
- **Ensembling logistic regression with XGBoost** (simple probability averaging): -3.8pts. XGBoost alone is meaningfully weaker on this feature set (61.8%), so blending drags the stronger model down rather than adding complementary signal.
- **NextGen Stats** (player-tracking data): tested 5 metrics — QB time-to-throw, QB aggressiveness, WR separation, WR YAC-over-expected, RB rush-yards-over-expected. All showed weak correlations (strongest was 0.08, `away_aggressiveness`). Building and testing the strongest candidate (QB aggressiveness) in the full model: no gain (68.2% → 68.1%).
- **`defense_process_advantage`** (Madden-style team-level composite: an Elo-style rating built from `def_sacks`, `def_qb_hits`, `def_tackles_for_loss`, `def_interceptions`, `def_pass_defended`): a single held-out split showed a promising +0.16pt accuracy gain with no change to log loss/Brier, but **5-fold cross-validation revealed the gain was well within fold-to-fold noise** (CV accuracy delta +0.0013 against a ±0.0118 noise band; log loss and Brier both slightly *worse*). Rejected. Player-level position grading (full O-line/DL/LB/secondary "Madden ratings") was considered as a next step but not pursued — the team-level version, built from the same underlying stats, already failed to show value, and free per-player O-line blocking data doesn't exist outside proprietary sources like PFF anyway.

**Investigated on suspicion, kept after testing:**
- **`home_wr_height_advantage` / `away_wr_height_advantage`**: a routine feature-contribution review flagged these as suspicious — near-zero, and univariately correlated with `home_win` in the *wrong* direction (home: -0.018 where positive was expected; away: +0.046 where negative was expected), with non-monotonic bucketed win rates. A proper held-out test (with vs. without, same methodology as the `spread_line` test) showed the opposite of what the correlation suggested: **removing them made log loss and Brier score slightly worse** (0.6335→0.6355, 0.2218→0.2228) with accuracy unchanged. Kept. **Lesson**: a weak/wrong-signed univariate correlation doesn't mean a feature is useless in a multivariate model — logistic regression can still extract value from a feature that only matters in combination with others, and the empirical held-out test is the authority, not the raw correlation.

**Did help — refining the existing best signal, and incorporating an external market signal:**
- **Margin-of-victory Elo**: standard win/loss Elo treats a 1-point win the same as a 30-point blowout. Switching to the FiveThirtyEight NFL formula (update scales with `ln(margin+1)`, dampened by how large the pre-game rating gap already was) gave a real, if modest, gain (+0.2pts) and a more historically sensible rating (2016 Cleveland's Elo dropped from ~1364 under plain Elo to ~1232–1252 under MOV — a more accurate penalty for a team that likely lost many games badly).
- **Splitting Elo into separate offense/defense ratings**: instead of one combined team-strength number, track two — offense (points scored vs. expectation, adjusted for opponent defense) and defense (points allowed vs. expectation, adjusted for opponent offense). Adding this *alongside* combined Elo hurt (-1.2pts, redundant/conflicting information) — but *replacing* combined Elo with it entirely gave a further real gain (+0.3pts on top of MOV Elo). **This is the current production Elo implementation.**
- **`spread_line` (Vegas's point spread) as a raw model feature**: rather than only comparing the model's output to Vegas as an external benchmark, `spread_line` itself is now fed into the logistic regression alongside the engineered features. It's not redundant the way the hand-computed interaction terms were — a market spread encodes information the model's box-score-derived features structurally can't see (late-breaking injury/practice news, situational factors, the aggregated judgment of professional bettors), so it supplies a genuinely new residual signal rather than a recombination of existing ones. Held-out test: accuracy 63.7%→64.7%, log loss 0.636→0.634, Brier 0.223→0.222. **Framing note for explaining this feature**: the model isn't "beating" Vegas by using its own line — it's partially deferring to the market on the parts of the game only Vegas can see, which is a legitimate and explicitly-acknowledged modeling choice, not a shortcut to hide.

**The clear, honest takeaway from this whole investigation: the real, durable gains came from (1) refining the model's single best signal (Elo) twice in succession, and (2) incorporating one genuinely external, information-rich signal (the Vegas line) — not from accumulating more unrelated box-score stats, more complex algorithms, or clever combination tricks. For this project's data size (~2500-3000 training games) and feature count, "build a better team-strength rating" or "bring in outside information the feature set structurally lacks" are meaningfully higher-leverage directions than "add another derived stat" or "try a fancier model."**

## ⚠️ General Rule: "Conditional" Features Require Gap-Aware Projection

Discovered independently twice (star WR injury, two-minute-drill comeback). Some features only naturally have a value in a specific **triggering situation** (a player is injured, a team is trailing late). Merging such a feature directly by `game_id` means the mere *presence* of a value leaks the outcome — e.g., a team only having a "comeback rate" value for games where they were trailing late means non-missing values are disproportionately attached to games the team was already losing.

**Fix:** use `pd.merge_asof(..., direction='backward')` to project each team's/player's last known value forward across **every** game they're part of, not just the games where the trigger happened. Check for this risk before building any future injury- or rare-situation-based feature.

## Core / Identifier Columns

| Column | Description |
|---|---|
| `game_id` | Unique ID (format: `season_week_awayteam_hometeam`) |
| `season` / `week` / `gameday` | Season, week, date |
| `home_team` / `away_team` | Original/historical team codes |
| `home_team_std` / `away_team_std` | Standardized codes for relocated franchises |
| `home_score` / `away_score` | Final score |
| `home_win` | **Target variable** |
| `home_coach` / `away_coach` | Head coaches |
| `home_rest` / `away_rest` | Days of rest |
| `div_game` | `1` if divisional matchup |
| `spread_line`, `*_moneyline`, `total_line` | Vegas market lines — `spread_line` is now a **model feature** (see above); the moneylines/total remain benchmark-only |

### ⚠️ Team-code convention warning
- **`load_team_stats`, `load_player_stats`, `load_snap_counts`**: backfill to the current code. Merge on `home_team_std`/`away_team_std`.
- **`load_pfr_advstats`, `load_nextgen_stats`**: use the actual code at the time. Merge on raw `home_team`/`away_team`, or verify via `team_abbr` matching against a team-game lookup.

## Engineered Features (Currently in the Model)

### Team-Strength Ratings — `add_elo_features` **(current implementation)**
Split offense/defense ratings, replacing combined Elo. Each team gets two separate numbers, both starting at 0 (league average):

| Column | Description |
|---|---|
| `home_off_rating_pre` / `away_off_rating_pre` | Points scored above/below league average, adjusted for opponent defense quality |
| `home_def_rating_pre` / `away_def_rating_pre` | Points allowed below/above league average, adjusted for opponent offense quality |

Updates use actual-vs-expected points each game, with a margin-of-victory-style learning rate (`k_off_def=0.05`), and revert 1/3 toward 0 at each season boundary. Historically validated: 2016 Cleveland's defense settles around -3.4 to -3.9, near the bottom of the real league range (~-4.8 to +4.9). **Kept as two separate numbers (not recombined) since a future live in-game model would likely want offense/defense tracked independently.**

*(Prior implementations — plain win/loss Elo, then margin-of-victory combined Elo — are retired; see Model Performance Summary for the reasoning trail.)*

### Team Recent Form, QB, RB, WR/TE, Injuries, Defense, Coaching, Rest, O-Line, DB/WR Matchup, Star Injuries
Unchanged this revision except where noted below — see the codebase (`src/features/`) for full detail on each.

### Injury flags — `home/away_qb_injury_flag`, `_rb_injury_flag`, `_wrte_injury_flag`
Flags whether each team's *current starter* (QB1/RB1/WR1-or-TE1 by depth chart) carries an Out/Doubtful/Questionable designation. Simplified this revision from an earlier "top-2-by-snap-share" definition to a straightforward depth-chart-based starter identification, since a dip in a team's actual starter should drop their expected performance regardless of how recently a backup logged snaps. Matched by stable `gsis_id` (not name) to avoid Jr./Sr./nickname mismatches. **These are real, correctly-computed features during training** — see the Live Prediction Pipeline section below for a serving-side bug that used to zero them out at prediction time.

### Star RB/WR injury flags — `home/away_star_rb_injured`, `_star_wr_injured`
Deferred at serving time (see below) — need a league-wide percentile ranking (top 10%/5% of ALL RBs/WRs that week), which requires cross-team computation beyond a single matchup's two teams. Always `0` in live predictions currently; real historical values used during training.

### Weather & Climate Shock, Red Zone Efficiency, Two-Minute-Drill Comeback Rate, `defense_process_advantage` — built, NOT in production model
All verified real signals or, in the case of `defense_process_advantage`, verified as noise via cross-validation. Redundant with team-strength ratings once combined in the full model, or (for `defense_process_advantage`) not distinguishable from chance. Code preserved for reference; excluded from `train_model.py`'s `FEATURE_COLS`.

## Live Prediction Pipeline (`src/predict_engine/`)

The live pipeline is split into `snapshots.py` (builds each team's "current state" — form, ratings, current starters, recent stats — once per prediction run) and `matchup.py` (assembles one feature row for a specific upcoming game from those snapshots and runs it through the trained model).

### ⚠️ Bug history: "most recently played" vs. "actual current starter"
Fixed for **QB**, **WR**, **TE**, **RB**, and **CB** using `nfl.load_depth_charts()` instead of "whoever played most recently" (breaks when an injured starter is replaced by backups late in a season — real example: KC's Mahomes injury, and Atlanta's move to a 3rd-string QB).

### ⚠️ Bug history: `nflreadpy` depth-chart schema instability
`nfl.load_depth_charts()` returns different column shapes depending on whether the season is archived/completed (`club_code`/`position`/`depth_team`, no per-update timestamp, CB has no L/R split) vs. the live in-progress-season feed actually used in production (`team`/`pos_abb`/`pos_rank`/`dt`, WITH L/R split like `LCB`/`RCB`). `safe_load_depth_charts()` normalizes both shapes to the original (live-feed) column names so the rest of the pipeline doesn't need to branch on season. Also fixed: `requirements.txt` previously left `nflreadpy` **completely unpinned**, meaning a future dependency update could silently break `build_snapshots()` (called once at app startup) and take the whole live site down on a routine redeploy. Pinned to the exact, locally-verified-working version.

### ⚠️ Bug history: real injury flags were computed but never served
`home/away_qb_injury_flag`, `_rb_injury_flag`, `_wrte_injury_flag` were correctly computed from real historical data during **training**, but were **hardcoded to `0` at serving time** in `matchup.py` — a real, trained-on, presumably valuable feature was contributing nothing to live predictions. Fixed by identifying each team's current starter via the same depth-chart data already available from `snapshots.py`, then matching by `gsis_id` against a league-wide weekly injury-designation set (`get_injured_player_ids()` in `injuries.py`, fetched once per week rather than per team). Verified against real-world context after the fix (e.g. Atlanta's 3rd-string QB situation correctly flagged, matching ESPN's analytics).

**Current limitation:** star-injury features (`_star_rb_injured`/`_star_wr_injured`) still default to `0` in all live predictions — deferred, see above.

## Known Data Quality Notes

- **Relocated franchises**: see team-code convention warning above.
- **Missing values**: filled with column means (`SimpleImputer`), except `home_coach_h2h_wins` (neutral `0.5`).
- **"Primary player" selection ties**: filter to the correct position/group with `inner` merge before selecting.
- **Live snapshot aggregation order matters**: team-level features must aggregate to one row per team-game *before* rolling.
- **Conditional/triggered features need gap-aware projection** — see dedicated section above.
- **NextGen Stats team-code matching**: match by `team_abbr` + season + week against a team-game lookup table, NOT by season+week alone — merging without the team key duplicates a single player's stat line across every game played that week league-wide (caught before merging into the model).
- **Vegas comparison caveat**: implied probabilities from moneylines aren't de-vigged/normalized.
- **Unpinned dependencies are a live-site risk**: `nflreadpy`'s schema has changed shape between versions at least once; any dependency called at app startup (as `build_snapshots()` is) should be pinned to a version that's actually been tested, not left to float.
